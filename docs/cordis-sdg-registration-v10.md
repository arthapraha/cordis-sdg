## 1. The question the entry answers

> **Which SDG concepts from the EU Vocabularies SDG taxonomy does each Horizon Europe project address, and why — in a way a non-technical reader can check?**

The page carries **nine numbered evaluation criteria**: (1) correct use of the SDG taxonomy, (2) quality of the mapping, (3) explainability, (4) reusability, (5) data handling, (6) visualisation and communication, (7) awareness of limitations, (8) a working web-based prototype, (9) a description document. Transparency and reproducibility are NOT numbered criteria — they appear under the page's methodological guidance and run through all nine. **Scale is not scored**: no criterion mentions corpus size, coverage or project count. That reading was counsel's and the builder verified it from the page at seq 37. This entry is scoped to be checkable rather than large.

## 3. The method — decision deterministic, prose by model

**The mapping DECISION is made by rules a reader can run by hand. A language model writes the explanation of a decision already made; it never makes one.**

1. **Crosswalk.** A table from EuroSciVoc categories to SDG targets, built once, every row with a one-line justification citing the target's text, reviewed by Hermes (§4.6) before use, committed as data. The first of two load-bearing artefacts, reusable by CORDIS on its own.
2. **Synonym list and key terms — the second load-bearing artefact.** SDG target labels are long UN sentences and will not fire whole against project text. Matching therefore runs against **key terms extracted from each target's label by a stated, committed rule** plus **a curated synonym list per target**, both committed as data and reviewed. The extraction rule is written down before it is run.
3. **Stop-list and negation rule, committed before the run.** Words that appear incidentally across Horizon Europe objectives ("sustainable", "water", "energy", "health", "growth" and their kin) are on a committed stop-list and count only in stated contexts; a committed negation/context rule says when a match near a negation or a "not related to" phrase is discarded. **Both exist before the first full run and change only by amendment to this registration.**
4. **Lexical evidence.** **Objective, title, keywords, the editorial description (§2's four reports fields) and the deliverable descriptions** are matched against §3.2's terms; every match is recorded as the exact phrase found, **with its source field**, so a reader can see which text carried the evidence. **The description and the deliverables are named here because §2 admits them and justifies the widening by criterion 2's penalty for "superficial keyword matching only" — a registration that declares a field in scope and then specifies a matcher that ignores it claims to answer a criterion it does not answer.** They are also the fields most likely to over-fire, which is what §3.3's committed stop-list and negation rule exist for; the per-field record above is how that is checked rather than assumed. **Coverage is partial and is recorded rather than assumed (v8):** at the snapshot the reports distribution covers about 41% of projects (measured on its CSV rows at seq 75; the JSON's own figure is measured and reported by the fourth fetch, and "about" is carrying that difference) and the deliverables about 48%. A project is matched on the fields it has; **every mapping row records which of the five sources were present**, so a reader can tell an absence of evidence from an absence of text, and §3.6's count of independent evidence sources runs over present fields only.
5. **Score and assignment.** Evidence per (project, target) is combined by a fixed weighting stated in the notebook; a target is assigned above a stated threshold; its goal is assigned with it; §2's cap applies. **Weights, threshold, extraction rule, stop-list and negation rule are tuned on the development set only (§4.2) and then frozen by Attila's word before the evaluation set is scored.**
6. **Confidence, and what an ambiguous project does.** A three-band label (high / medium / low) derived from the score and the number of independent evidence sources **counted over the fields present for that project (§3.4), never over the five**, stated as a rule. **A cross-cutting project — evidence for several targets across different goals — keeps them all up to §2's cap and is reported as cross-cutting. An ambiguous one — evidence too thin for any target above threshold — is assigned at goal level where a goal is supported and left unassigned where none is, and both counts are reported.** The page asks the method to show how it deals with ambiguous and cross-cutting projects, so the treatment is registered rather than described afterwards.
7. **Explanation.** For each assignment the model receives only the evidence rows and writes two sentences a non-technical reader can check against them. Model name, version, prompt text, parameters and the prompt's hash are recorded in the repo and on every row. **The model sees no project the rules did not already map, and its output cannot add or remove an assignment.**

Anything the model is asked to do beyond §3.7 is a separate, labelled, non-primary column and a change to this registration.

## 4. Validation — development and evaluation, and a seal that blocks the read

1. **Sample.** One seeded draw of **150 projects** from the snapshot, the seed and the draw recorded in the notebook. Split by the same seed into **50 development** and **100 evaluation**.
2. **Development set (50).** Labelled by Hermes and counsel, **each set uploaded and hashed before either is revealed**, and posted **unsealed** once both are in. **The ordering is what makes §4.7's agreement figure mean anything**: §4.4's blindness clause binds only "before their own are sealed", and development labels are never sealed, so without this line the second labeller could read the first set and the reported kappa would be a measure of nothing. Independent production is a rule here, not an assumption. §3's weights, threshold, extraction rule, stop-list and negation rule are tuned against these 50 and nothing else. Reported, but not the headline.
3. **Evaluation set (100).** Labelled blind by **Hermes**, with **20 of the 100 also hand-labelled by Attila** as the human anchor. **Counsel does not label this set** — §4.4 says why. **THE ORDERING IS THE MECHANISM AND IT RUNS ONE WAY: the freeze word is spoken FIRST, and only then is any evaluation label set uploaded and hashed.** Nothing can be tuned to a set that does not yet exist, so the guarantee does not rest on anyone declining to look. **Sealed also means unread: the builder does not fetch, open or read any evaluation label artefact until the frozen pipeline has run once on the 100 and its output artefact hash is posted.** (v2 stated both orderings in this paragraph; the one above is the rule.)
4. **What "blind" cuts.** Labellers do not see the pipeline, its output or each other's labels before their own are sealed. **Labellers may have seen the reviewed crosswalk**; the registration says so rather than pretending otherwise, and Hermes's crosswalk pass is scoped in §4.6 to leak as little as possible. **And counsel cannot be an evaluation labeller at all:** its standing duty is to read every build hash from its own worktree, which IS the pipeline, so a counsel label on the evaluation set would come from the one seat guaranteed to have seen the method and its code. v2 caught this conflict for Hermes and missed it for counsel. **Counsel therefore labels the development 50 only**, where labels are used for tuning and contamination costs nothing.
5. **Hand-off, and what it now costs.** Code_Cordis posts the drawn sample as an artefact: project ids plus the §2 fields, no scores, no pipeline artefacts. **Since v4 admitted the editorial description and the deliverables, that artefact carries full prose for 150 projects — objective, the editorial description where present, the deliverable descriptions where present — and every labeller reads all of it, with each project's absent fields marked absent so labellers and the pipeline read the same text (v8)** — materially more work than v2's objective-and-keywords, landing on §8's ratification-plus-four-days row. Stated here before the date rather than discovered on it. **All labellers work from that artefact and nothing else**, so labels are made from exactly the fields the pipeline sees. Labels are posted as **id → list of target URIs**, no justifications, so the agreement metric is clean.
6. **Hermes's crosswalk pass** is a justification-versus-taxonomy check: does each row's reason cite concepts that exist in the taxonomy snapshot and relate as claimed. It is not a re-derivation of the crosswalk.
7. **Metrics, with their unit.** The unit is one (project, target-URI) pair. **Inter-rater agreement**: pairwise, exact target-URI match, reported as agreement rate and Cohen's kappa between each pair of labellers; goal-level agreement as a secondary figure. On the **development 50** that is Hermes against counsel. On the **evaluation 100** it is Hermes against Attila **on his 20 only**, since he is the only other labeller there — a thin overlap, reported with its n and never presented as agreement over the hundred. **Pipeline precision and recall** against the adjudicated evaluation labels at target level, goal level secondary; confusion cases listed by project id. Agreement against Attila's 20 reported separately as the human anchor.
8. **Adjudication.** On the evaluation 100: for the 20 Attila labelled, a disagreement between him and Hermes is settled by **Attila's call**; for the other 80, **Hermes's labels are the reference**, and the report carries that as a limitation. On the development 50, a disagreement between Hermes and counsel is settled by **Attila's call** where it changes a tuning decision and recorded unresolved where it does not. The rule is stated here so it is not chosen after the numbers are in view.
9. **No acceptance threshold.** This is a report of what the method does, not a gate it must pass; a poor number is submitted with its explanation, because the organisers score limitation awareness.

## 5. What is out of scope and why

- **FP7 and Horizon 2020.** Allowed by the rules, excluded here for size; the notebook says how the method extends.
- **Model-made assignments.** Excluded from the primary mapping by §3; may appear as a labelled comparison column if time allows, never as the answer.
- **Indicator-level output that no reviewed row supports.** §2 admits an indicator only where a reviewed crosswalk or synonym row exists at that level. Unreviewed precision is worse than none, which was Hermes's point at seq 16 and survives the change.
- **Any personal data.** **Person-level fields are not read.** Participating organisations and their countries are read, because an organisation is not a person and the page's rule is "participants must not process personal data" — the CORDIS sense of "participant" is an organisation, and §2 admits it for the analysis dimensions the page names. v4 corrected §2 and left this bullet standing.

## 9. Ceilings

- **Tokens:** the explanation pass is bounded by the row count; a per-run ceiling is stated in the notebook before the full run and the run parks past it.
- **Provider:** any hosted model is acceptable to the rules if documented; the pipeline records provider and served model per row.
- **No credentials in the repo or the room.** Keys are read by name from the environment.
- **Our own licence, which criterion 4 rewards and nothing registered until now.** The page requires none and encourages one. **Proposed, and Attila's to settle: CC BY 4.0 for the documentation, the crosswalk and the synonym list; MIT for the code.** Stated in the README and in the description document.
- **The LLM rule rests on Q11, not Q4.** Q11: all LLMs, open or closed, may be used, and the requirement is that the methodology is transparent and reproducible; it warns that a commercial API's reproducibility has inherent limits because the provider may change the model. Q4 read alone points the other way, so **the notebook cites Q11 by number**, and §3.7's per-row record of model, version, prompt and parameters is what answers it.
- **One name on the certificate (Q9).** Teams may enter; the certificate carries one person or a team name, and that choice is Attila's alone.
